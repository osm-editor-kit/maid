## What iD does

### On adding a way member (`modules/actions/add_member.ts`)

1. `actionAddMember` (line 10) sends a way that is not a PTv2 stop or platform to `addWayMember` (lines 18-20). Other members go to `relation.addMember(member, memberIndex)`; a PTv2 stop or platform without an index goes to position 0 (lines 22-29, the "hack" comment at 24).
2. `addWayMember` (line 37) takes all PTv2 stop and platform members out of the list (lines 41-50).
3. It groups the remaining members by type and pushes the new way at the end of the way group (lines 54-56), then calls `osmJoinWays(members, graph)` on **all** the way members, not only the new one (line 59). The comment at line 53 says "Just push and let `osmJoinWays` decide where to put it".
4. For each joined segment it finds where the segment starts in the member array (lines 66-73) and moves each later member of the segment to position `j+k` with `moveMember` (lines 76-86; moves at line 83, only when the slot differs). A moved member is marked dead (`index = -1`) and re-inserted (lines 108-119 explain the splice).
5. Dead entries are dropped (lines 92-98). The result is PTv2 stops and platforms first, then nodes, then the ways in join order, then relations (line 103). Relations therefore move behind all ways.
6. Ways that are not downloaded are not joined (the filter at `multipolygon.ts:10-12` keeps only entities that exist). They keep their array position, so they are not moved by the join.

So on every way add iD re-sorts the whole way list. An existing order error elsewhere in the relation is rewritten at the same time, and nothing reports it.

### `osmJoinWays` (`modules/osm/multipolygon.ts:37-138`)

- It takes the first remaining item as a sequence and repeatedly looks for the next item in array order (lines 91-119 in the loop; the first match wins).
- When joining members (not plain ways, see `joinAsMembers` lines 14-23 and the comment at 14-16, #4872) and the sequence has one way, it reverses the first way so the route keeps a forward path (lines 91-99, comment "for routes, it does. (see #4589)" at 88). The reversal is recorded as an action (`sequences.actions`) and does not change the member's order.
- It attaches an item to the end or the start of the sequence, by node identity only (lines 100-119). There is no backtracking, no Euler path, and no check whether a closed sequence can take more items.
- It returns sequences (components). Items that do not touch anything form their own sequence.

### On splitting a member way (`modules/actions/split.ts:287-425`, `splitWayMember`)

- Called for each parent relation of the split way (`split.ts:222` and `232`). It is local: only the new part (wayB) is inserted next to the old one (wayA). Other members are not moved. The comment at lines 276-285 says it assumes the members are already "properly" sorted.
- `connects(way1, way2)` (lines 291-307) is true when the two ways share an end node. A closed way with `junction=roundabout|circular` connects at any of its nodes (lines 292-301).
- The neighbours of wayA (previous and next member) are tested for connection to wayA and wayB. A 2x2 table (comment lines 336-352, code at 364-375) decides "insert after" or "insert before".
- If both neighbours connect to both ways (a loop), it looks one member further (lines 376-403).
- Otherwise it inserts by the orientation of wayA (lines 408-414).
- Insertions are applied in reverse index order (line 418).

### Other paths

- Drag-and-drop in the members list calls `actionMoveMember` (`modules/actions/move_member.ts`), which moves by index only (`raw_member_editor.js:370`).
- The membership list (`raw_membership_editor.js:238-250`) calls `actionAddMember(relationId, member)` with no index, so it takes the same way-join path.
- `join.ts` uses `osmJoinWays` for joining ways (not member lists); it reverses ways to make one line (`join.ts:53-56`).

## What iD does NOT do

- No automatic sort on load. The order of members is not compared with the geometry anywhere.
- No validation of member order. `modules/validations/*` was searched: no rule compares relation order with geometry. The relation-related rules are `disconnected_way.js` (routing islands via members, lines 137 and 157), `mismatched_geometry.js:425` (closed multipolygon parts, using `osmJoinWays`), and `crossing_ways.js:342` (members for crossing checks). `disconnected_way` and `mismatched_geometry` are about connectivity or closure.
- No check that the new way creates a loop, spur or gap.
- No duplicate check for members (#9311 was closed as "not planned").
- No fix offered for an order problem. Users reorder by hand (`move_member`).
- It does not use the geometry of the way (only the node ids of the way ends and of the closing node), except for the order of the join.
- Split and add take no account of the direction of travel beyond the connectivity table.

## Maid: what the chain does (read, with runs)

Read in code:

- `chain.ts:86-97` (`mainWays`): only `kind === 'main'` ways are chained (`roles.ts` `classifyMembers`; `stop`, `platform`, `subroute`, `branch`, `point`, `unloaded` are not). A way equal to the member before it is skipped (`chain.ts:91-92`).
- `chain.ts:100-102` (`canEnter`): a closed way can be entered at any node of its ring, an open way at either end.
- `chain.ts:105-115` (`joinNode`): for two closed ways it returns the first ring node of `a` that `b` can enter (`ring.find`, line 114). The choice is arbitrary when two closed ways share more than one node.
- `chain.ts:195-212` (`buildRuns`): a greedy pass in relation order. A way that can enter the current run's end extends the run (line 202). A one-way way that touches the run without continuing it is recorded as a parallel strand (204-205). Anything else starts a new run (207). A run never re-enters an earlier run.
- `chain.ts:215-251` (`endIndex`, `isConnected`): runs are connected only through their **end** nodes (`run.start`, `run.end`). A node in the middle of a run does not connect two runs.
- `chain.ts:305-321` (`joinAll`): if the number of odd-degree run-end nodes is at most two and the runs are connected, it tries a greedy walk from every run in both directions (`chainFrom`, 257-290), then falls back to Hierholzer's walk (`eulerPath`, 327-361). The first order found is returned; there is no check whether another order exists.
- `chain.ts:404-435` (`buildChain`): one run gives `yes`; several runs that join give `sorted` with `sortedOrder`; otherwise `no` with pieces in relation order and `gaps`.
- `place/issues.ts:74-86` (`orderIssues`): `sorted` gives one `order` warning listing the main ways whose place differs.
- `place/issues.ts:53-68` (`gapIssues`): every gap gives a `gap` warning, whatever the reason. `not-loaded` is a separate info issue.

## What this means for the owner's questions

- iD has no route-order validator. The overview is ahead of iD on this point, so the risk is only false warnings, not missing ones.
- The false warnings found (runs, all reproducible with the scratch scripts): out-and-back spur with the spur way listed twice (order warning), and a shuffled route with a junction inside a run (gap warning). An unloaded member in the middle gives a gap warning that may be wrong.
- The silent loss: a way listed twice in a row (a roundabout traversed twice, a spur) is dropped by `chain.ts:91-92`. It is not an error, but it hides a traversal, and any fix built on `sortedOrder` would drop it from the member list.

## Recommendations

### A "fix order" button must refuse when

1. A way id appears more than once in the main list. `sortedOrder` has one place per way; a fix would drop a traversal. (Covers spurs, roundabouts traversed twice, #10435, #9311.)
2. The line contains a closed way (roundabout or loop). The entry node is chosen by `ring.find` (`chain.ts:114`), and iD's own rule for closed ways is special (`split.ts:291-300`) and was broken in #8415.
3. More than one order gives a valid line: a loop of runs (all nodes even), a run network with a junction inside a run, or a choice of start (the square and lollipop rows above). The chain returns one order without saying so. A fix needs a uniqueness check first.
4. Any gap, or any main way not loaded (#7653). The order cannot be verified when the data is partial, and the gap may be a missing member, not a wrong order.
5. A parallel one-way strand (`parallel` not empty). `issues.ts:77-80` already leaves the strand out of the comparison; a fix must keep it in place.
6. Any PTv2 stop, platform, sub-route, branch or point member is interleaved with the ways, or any stop is out of sequence (#4864, #4946, #4978). A fix should move only main ways and keep the others where they are, or refuse.
7. The proposed list is not a permutation of the current members (same ids, roles and count). A fix must never add, remove or change a member.
8. Before writing, the proposed order must give `linear: 'yes'` when chained again, with no gaps. This is a cheap self-check and catches the cases above.
