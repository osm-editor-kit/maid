# Health run, 2026-11-28

An overnight run of `bun run check-all --app <app>` for every app in `APPS` (`tools/bench/args.ts`), from `main` at `b268c96`. Each failure was rerun up to three times to tell a flake from a real failure.

**Result: no real failure.** Every check of every app passes. Four checks failed once, all because the machine was overloaded, and passed on every rerun. One of them, `tooltips`, got a wider timing margin.

## Setup

Another session's `bun run dev` held 5176, 5177 and 5180, so this run used its own servers: the mock API on 8090 and the nine apps on 6173 to 6183 (default port + 1000). Two things were needed for that:

- **`MAID_APP_PORT`** (new, in `tools/bench/check-page.ts`): the port the checks open the app on, like the existing `MAID_MOCK_PORT`.
- **HMR port:** every app's `vite.config.ts` pins `server.hmr.port` and `clientPort` to the app's default port, so `vite --port 6176` still opens its websocket on 5176. When another server holds 5176, Vite logs `WebSocket server error: Port undefined is already in use`, and every check fails with the uncaught page error `WebSocket closed without opened` (the first bicycle run: every check had its full `ok` count but exited 1). For this run, each app got an untracked wrapper config that moved HMR onto the run's port. That wrapper was deleted afterwards and is not committed. See "Open" for a lasting fix.

Other sessions were running browser checks at the same time (load average 25 to 40). All my vite servers were also killed once, at 06:57, by a process outside this run, and I restarted them. So the times below are slow, and timing-sensitive steps are more likely than usual to flake.

## Fixed

- **`tooltips` flake** (`tools/bench/tooltips-check.ts`): the check read "no tooltip yet" 150 ms after the pointer moved onto a button, against an open delay of 400 ms (`OPEN_DELAY_MS`, `packages/ui/src/tooltip-group.ts`). On a busy machine, Playwright's round trips used up the 250 ms margin, and the check saw a tooltip that had waited its full delay (`FAIL hover Point (another group): no Point tooltip before the delay`). It now reads at 50 ms, which still catches a tooltip that opens at once, the bug this step guards against. It then waits 600 ms instead of 500 for the open tooltip.
- **`MAID_APP_PORT`** (`tools/bench/check-page.ts`): the browser checks can now run against an app server on another port.

## Open

- **HMR port pinned to the default port** (all nine `apps/*/vite.config.ts`): a dev server started with another `--port` cannot open its HMR websocket while the default port is taken, and every browser check then fails on an uncaught page error. A likely fix: drop `port` and `clientPort` from `server.hmr` and keep `host: '127.0.0.1'`, so HMR follows the server's port. That needs a check that the OAuth origin (`127.0.0.1:<default port>`) still works for a person, so it was not changed tonight.
- **Contention between sessions:** two sessions running `check-all` at once doubled check times and caused the one page-load timeout. Overnight sessions running browser checks should take turns.
