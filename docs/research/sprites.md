## 1. How Maid gets map images today (READ unless noted)

Totals: about 60 fixed images at start, plus a long tail made on demand (pins, bare icons, signs). Three different mechanisms (preload on style.load, `styleimagemissing`, `setMissingStyleImageResolver`) plus an "add before the layer names it" pattern for signs.

Icon source files (`packages/shell/public/sprites`, committed): 6 SVG `<symbol>` sheets cut from iD's by `bun run sprites-subset` (`tools/refs/subset-sprites.ts`, names from `tools/refs/icon-names.ts`). MEASURED: 574 KB raw, about 172 KB gzipped; 957 symbols (temaki 407, fa 198, maki 148, roentgen 101, iD 69, pinhead 34). `docs/research/first-paint-audit.md` and `review-performance.md` #7 already flag sprite download + DOMParser on the main thread + per-icon decode as a first-paint cost (their numbers are inferred, not measured).

Dimming of the lens / other levels is done with `icon-opacity` (`packages/renderer/src/layers.ts`, `dimmedByLevel`, `OPACITY` map), not with colour. No `sdf`, `icon-color` or `icon-halo` anywhere in the code (grep). So the "SDF recolouring for dimming" benefit does not exist for today's needs.

## 2. What tilda-geo built (READ)

In the tilda-geo repository, `app/`. No other sibling checkout contains sprite tooling (grep for spreet, spritezero, buildSprite).

- `scripts/map-style/buildSprite.ts`, run as `bun run map-sprite-build`. Plain TypeScript on **sharp** (libvips). No Rust, no spreet, no SDF.
- Input: `scripts/map-style/icons/*.svg`, 40 hand-managed SVGs (file name = id, kebab-case; `width`/`height` attributes = size on the map in px). Includes line/fill patterns (`pattern-*`), note icons, parking/bike badges, label boxes.
- Output: `public/map-style/sprite.png|json` and `sprite@2x.png|json` in the standard MapLibre sprite format (sheet 256 px wide, 1 px gap, rows tallest first; `{width,height,x,y,pixelRatio}`), plus `icons-overview.png`, plus a content hash written to `src/server/api/map-style/spriteVersion.const.ts`. The style response sets `sprite: <origin>/map-style/sprite?v=<hash>`, so MapLibre loads it natively and the hash busts the cache. Sizes MEASURED: sprite.png 16 KB, sprite@2x.png 35 KB.
- A vitest (`spriteIcons.test.ts`) checks every image id used by layers/styles exists in sprite.json.
- Generic or TILDA-specific? The **build script is generic** (about 150 lines, depends only on sharp, the SVG size convention and a folder). The **icon set, the style URL wiring and the version hash are TILDA's**. It does not do SDF, trimming, deduplication or multiple sprites.

## 3. Options

### (a) Keep runtime rasterising

- Replaces nothing. Gain: none. Cost: stays as is (sprite SVG fetch + parse + per-icon decode on the main thread; fixed ratio 2; 3 loading mechanisms). Works with the "no network" rule (same-origin files). Risk: none, but the first-paint cost in review-performance #7 stays.

### (b) TILDA approach (sharp, SVG folder to PNG+JSON, `sprite` in the style)

- Would replace: the ~60 fixed images (glyphs, cones, side markers, plaque, parking/lane/shapes arrows) if they were drawn as SVG files. Not the data-dependent ones (signs by value, pins by preset).
- Gain: MapLibre fetches one PNG+JSON and decodes it off the render path, no canvas code per image, the pixel ratio choice (1x/2x/3x) is MapLibre's; a hash gives cache busting. Fixed-image preload loop in `installDirectionImages` and the `style.load` re-adds go away (the style carries them). `line-pattern`s can be built at 1x/2x/3x.
- Cost: the glyphs are generated from code paths (`glyph.ts`, `glyphPaths`, state x tone variants), so there is a generator step (emit SVG, then rasterise) instead of SVG files by hand. Needs a Maid style with a `sprite` URL (Maid builds its style in code; `EMPTY_STYLE` in `MapView.tsx`) and a committed or generated output with a version. The 13 side markers and 38 glyph ids are generated, so the "icon" folder would be generated too. Output must be reproducible and `bun run` driven: fits.
- Risk: low to medium. Image ids unchanged, so layers stay. The direction work on this branch (`direction-images.ts` just rewritten) is churning; moving it now means doing it twice. A fixed sprite needs a build step before `check` and the benchmark.
- Note: sharp is already available in the Bun ecosystem; the 3 JS dependencies (sharp, no Rust toolchain) are simpler than Rust.

### (c) Rust CLI (spreet) with SDF variants

- From memory (not fetched; I did not read the README this session): spreet (github.com/flother/spreet) is a Rust CLI and crate that reads a directory of SVGs and writes `name.png` + `name.json`; flags I recall are `--retina` (also writes @2x), `--unique` (de-duplicate identical icons), `--minify-index-file`, `--sdf` (the sprite as signed distance fields, via the library's SDF support), `--recursive`, `--ref-pixel-ratio`. Binary release, `cargo install`, Docker. Check the README before relying on any flag. `cargo` and `rustc` are installed on this Mac; `spreet` is not.
- Would replace: same set as (b), and it could pack the **957 symbol icons** too if the iD symbols were split into one SVG per icon at build time (a script, `sprites-subset` already reads the symbols). Result: bare vertex icons become static sprite images with no runtime decode.
- Gain over (b): SDF variants, fast packing, `--unique`. But SDF gives only single-colour recolouring. Maid does not recolour today (dimming is opacity). The glyphs are two-colour (edge + fill); SDF cannot do that (only `icon-halo`, which is thin and blurry), and the lane arrow comment already says a filled shape looks cut as SDF. Pins are white + grey outline + #333 icon, a composite, not SDF-able. Realistic SDF candidates: the bare `icon-<icon>` vertex icons and the single-colour parking arrow, which could take `icon-color` for dark map / selected states. That is a possible future need, not a present one.
- Cost: a non-JS tool in the build chain (Rust binary, must be installed by `refs-setup`-like step or a pinned download; AGENTS.md wants everything a `bun run` and no network in automated runs, so it would need a vendored or cargo-built binary, a person doing the fetch once). Extra CI install step. Same generator step as (b) for generated glyphs.
- Risk: medium (new toolchain, how it handles the iD symbols' `<defs>`/`use` is untested, anti-aliasing and quality of SDF at 12 px is untested).

### (d) Other

- `map.addSprite(id, url)` exists in MapLibre in this repo (node_modules maplibre-gl 6.12.0 d.ts lines 10310 and 15543; packages ask for ^6.16.0): lets a module ship its **own** sprite, loaded when the lens/module opens, images named `<spriteId>:<name>`. That fits Maid's modular design better than one global style sprite (bike module has its own signs/arrows; lanes its own arrow). Combined with (b): one core sprite (directions, cones, plaque, side markers) and optional module sprites (parking, lanes, shapes handles, bike).
- Keep `setMissingStyleImageResolver` for the data-dependent long tail (pins by preset, signs by value, Mapillary icons). It is the right tool there (MapLibre waits for the promise during tile layout).
- Unify the three "missing image" mechanisms (preload + `style.load`, `styleimagemissing`, resolver) into the one resolver. That is a code cleanup, independent of sprites.
- Pin sheets: pre-compose pins at build time for the preset icons actually used (a subset, since pin + icon must stay one image so MapLibre places and hides them together). Only worth it if measurement shows pin creation dominates the first paint.

## 4. Recommendation

**Not now for a Rust/SDF sprite; yes later for a build-time sprite of the fixed images, but measure first.** Facts: Maid's biggest image load is the on-demand pin/icon rasterising and the 574 KB SVG sheets; the ~60 fixed images are cheap canvas draws built once and are changing on this branch; no SDF need exists; TILDA's script solves the _fixed_ images only.

First concrete step (one hour, read-only measurement, no integration): add a measurement of what the current path costs on a cold load (the load benchmark `bun run bench` / `bench-smoke` with the marker images: time from first request to last `addImage`, count of images made, main-thread ms for `loadSprite` + `makeIconImage`). `docs/research/review-performance.md` #7 and `first-paint-audit.md` give only inferred numbers. If that shows tens of ms or more, then the step after is (b)+(d): a `bun run sprite-build` using sharp (as in TILDA, no new toolchain) that emits the fixed images (direction glyphs and cones, side markers, plaque, arrows) into a core sprite and per-module sprites via `addSprite`; try spreet only if SDF recolouring becomes a real requirement (for example a dark map). Do not do it while `direction-images.ts` is still being redesigned (AGENTS: finish the step first).

Still unknown (not measured): actual first-paint cost of the SVG sheets; the PNG size of a 957-icon sprite (inferred: low hundreds of KB at 2x, so no saving over the 172 KB gzipped SVG, and it would load fully rather than only the used sets); spreet's exact flags and SDF quality at 12 px.
